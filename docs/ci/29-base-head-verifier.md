## Head verifier with the nightly red list

`pstack-verifier.yml` drives the pull request head, then re-drives only the side journeys that failed on the head against the production base, so a journey already broken in production can no longer block a pull request. Production redness also comes from the daily feature-map live pass (`.github/workflows/feature-map-live-daily.yml`).

Jobs: `resolve`, `plan`, `drive`, `judge`, `mark`, `post`, `cancel`. The head drive belongs to `drive`; the base re-drive and its `base-evidence.json` belong to `judge`. There is no separate base job and no base cache. A plan that holds no journey skips `drive` and the judge's `judge-ask` step, so the judge decides on the required checks alone. A run that leaves no verdict artifact posts the error status `verifier could not evaluate: the judge lane did not produce a verdict`, never a failure that names nobody.

Journeys come from the feature map. The plan lane reads `.claude/skills/verify-hypertask/features` from the production checkout, never from the candidate, and picks the pages whose code the pull request touches: a changed flag definition, a flag key in a changed line, a named source or API path, a named component directory, or a distinctive file name. A test file never selects a page, and a flag-looking file name is not a flag key, because nearly every page names its own tests. At most six pages are planned, highest score first, so one plan stays inside the lane timeouts. A page whose plan cannot be read is logged and skipped; it does not throw away the pages that were read. Each matched page gives one `area:<page>` journey planned from that page's own text, so the same page always gives the same script. One `change:primary` journey is planned from the pull request, and a `[BUGFIX]` title plans `change:repro` instead: the repro must pass on head. A change that matches no page keeps the change journey alone.

Before the change journey is planned, the plan lane traces each changed library file through its importers, two hops at most, to the `src/pages` or `src/app` file that uses it, and names the feature page that mentions that file. The planner reads that trace, so a library change is never called a non-app change while an importer reaches a screen or an API route. The planner also reads the seeded fixtures: `{id}` is the active board, `{task}` is a task on it and `{archived}` is the archived board. It may plan setup actions as `api` calls, and a body value that is exactly one of those placeholders becomes a number, while the same placeholder inside a longer string stays text.

The drive lane boots the head as its candidate with the production checkout as its trusted root. A trusted root counts only when its `node_modules` holds an npm install; an empty directory installs the candidate's own dependencies inside the container instead of booting without them. A journey is unavailable when the preview did not start, failed at its first failing step or expect, unjudged when the model did not answer, otherwise ok. Every step that passes is still judged by the model and prompt, with the run's own screenshots. The drive lane writes the head evidence only; it never previews the base commit. A plan whose actions are all `api` calls has no screen, so its text expects are matched against the response text of those calls instead of page text.

The judge lane asks the model about every head journey it has not judged yet and records each verdict in the head evidence, so a journey can fail on the model's reading alone. A plan that needs no drive has no head evidence and no journeys to ask about, so the ask lane records nothing and the judge settles that plan from the required checks alone. `base-plan` then writes a filtered `base-plan.json` for at most four failed `area:*` side journeys (never `change:*`), whether a scripted step or the recorded model verdict failed them, checks out `base.sha` as `candidate-base`, re-drives only those journeys once against the production base, and saves `evidence/base-evidence.json`. The judge step then decides once, reusing the verdicts already recorded. The judge lane also reads the newest completed daily live pass and its `feature-map-live-<run>` artifact, then uses `result.json` as the list of features already red on production. Both the run list and the artifact come through `gh` with `actions: read`. A missing artifact, an expired artifact or a failed download leaves the red list empty, and an empty list never excuses a failure. If `evidence/base-evidence.json` is present and matches the run binding, a failed `area:*` side journey whose production base run also fails (any step) is recorded as `<journey> also fails on production` instead of a problem, up to four side journeys per run; if production passes it, it stays a problem.

Verdicts:

- every journey passed on head: PASS.
- a head journey failed for a feature the newest nightly pass also fails: PASS+NOTES naming it, because the nightly live pass owns that feature. It does not block the pull request.
- a failed `area:*` side journey that also fails when re-driven against the production base (at most four per run): PASS+NOTES naming `<journey> also fails on production`.
- a head journey failed for a feature the nightly pass passes and production base passes (or beyond the four re-drive cap), or for the change journey itself: FAIL. The change journey and a bug fix repro have no feature page and are never excused by production base or the nightly red list.
- a lane that never ran, or a judge model that did not answer: the run could not evaluate the change, so the status is error and the recheck drives it again; it is never a FAIL on the change itself.
- a bug fix with no planned user path, in a diff that ships app code: PASS+NOTES when every required check is green and the `repro-first` job shows a changed test failing on base and passing on head, because that test is the proof where a journey is not practical, whether the plan holds area journeys or none. Without that test the run is FAIL and names the missing test. A `[BUGFIX]` whose file list holds nothing under `src/`, no API route, no page and no shipped asset plans no repro journey, asks no model, and settles like any non-app change.
- a change that reaches a screen but whose plan found no user path: the run could not evaluate the change, so the status is error, never FAIL on the change itself.
- non-app files only, and a `[BUGFIX]` with no app code: PASS+NOTES, no app path.

An identical diff is not an identity: a rebase onto a new base can bring production files the diff never shows, and `git patch-id --stable` ignores whitespace inside a value. Reuse is therefore anchored on the head tree, and the recheck re-runs a green head whose base has moved.
