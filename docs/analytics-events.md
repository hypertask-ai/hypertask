# Server invite and subscription analytics

HTPR-7268 cutover (2026-10-16): flag `htpr-7268-invite-seat-analytics` (https://app.hypertask.ai/admin/flags#flag-htpr-7268-invite-seat-analytics). For a user with the flag on, `invite_sent` replaces `teammate_invited`, `member_joined` replaces `invite_accepted`, and the three Stripe events are sent; with the flag off, the old two invite events continue unchanged and no Stripe event is sent. The cutover date per user is when the flag reaches them; historical events are unchanged. Contract: `ht-marketing/seo/tracking/tracking-plan-2026-10-16.html`, commit `14b6866`.

All five events use `distinctId=String(user_id)` and include `user_id`, `workspace_id` (team ID), `board_id` (project ID or null), `source=server`, `event_id` (event name plus business ID), `occurred_at` (ISO), and `environment` (`VERCEL_ENV`, then `NODE_ENV`, then `unknown`). IDs are strings. The contract also requires `utm_source`, `utm_medium`, `utm_campaign`, `initial_referrer`, `is_seeded`, `account_category`, and `attribution_status`. There is no cheap existing attribution/category/seed classifier at these boundaries: those values are null, with `attribution_status=unknown`, rather than inferred. Names, emails, tokens, credentials and free text are never included.

| Event | Trigger and business ID | Additional properties |
| --- | --- | --- |
| `invite_sent` | Accepted email delivery or successful public-link creation; invitation ID. Resends and link reuse do not count again. User is the inviter (the actual creator for public links). | `invitation_id` (a one-way SHA-256 pseudonym of the invitation ID, because the raw ID is the invite link key), `invite_method=email\|link`, `role` (current invite paths create the schema-default `Member` role) |
| `member_joined` | A committed invited/shared/direct human board membership; membership row ID. User is the joiner; the board owner's own membership is excluded. | `membership_id`, `invitation_id` (same pseudonym as `invite_sent`; null for share/direct adds), `inviter_user_id` (null when unavailable), `role`, `member_count` (accepted human board members plus the owner, excluding agents) |
| `subscription_started` | Verified `invoice.paid` that is the subscription's earliest positive paid invoice in the customer's Stripe history (renewals of subscriptions paid before this change never count; a truncated history skips the start), with positive `amount_paid`, a stored customer mapping, and an active subscription with positive discounted recurring amount; subscription ID. Trials, free invoices and full discounts are excluded. | Stripe fields below, `invoice_id`, `amount_paid`, `paid_at`, `is_first_subscription_for_user`; `seats_before=0` |
| `subscription_seats_changed` | Verified `customer.subscription.updated` with different known before/after quantities; Stripe event ID. The before quantity comes only from `previous_attributes`, never the current database. | Stripe fields below |
| `subscription_canceled` | Verified `customer.subscription.deleted` with an actual `ended_at`; subscription ID. Scheduled cancellation alone does not count. | Stripe fields below, `canceled_at=ended_at` (ISO), `cancellation_reason` (Stripe reason category or `unknown`); `seats_after=0` |

Every Stripe event includes `stripe_event_id`, `stripe_customer_id`, `subscription_id`, `seats_before`, `seats_after`, `plan` (first item's price ID), `interval=month|year` (null if unavailable or mixed), `currency`, and `discounted_amount` (integer minor units per billing interval across all items, after item/subscription percent-off or amount-off coupons). Unexpanded discounts or unknown amounts produce null, not an undiscounted guess. Account-level Stripe events have `board_id=null` and resolve `workspace_id` and the billed owner only through `team.stripe_customer_id -> team.googleAccount.userId`, never email. Unmapped customers are skipped with one data-free warning; no marker is consumed, so replay after mapping can succeed. Payment order uses `status_transitions.paid_at` (then `created`, then invoice ID for ties). `is_first_subscription_for_user` is false when the same Stripe customer paid another subscription earlier, null when the paid-invoice history is truncated or the billed user owns another workspace with its own Stripe customer, and true otherwise. With the flag off, legacy `teammate_invited` keeps its original per-route attribution (caller for email and resend, stored owner for public links).

All work is scheduled with `scheduleAnalytics`, outside invite/webhook response latency. Successful captures write a logs-table marker under advisory locks; retries use a deterministic PostHog envelope `uuid`. Business keys dedupe independently of the attributed user; existing activation markers and UUIDs are unchanged. Failures leave the occurrence retryable on replay; this change does not add an automatic retry queue or historical backfill. The existing `isActivationEligible` flag/guest/QA gate still applies, plus the HTPR-7268 flag for the billed, inviting or joining user.

## Covered join and invite paths

- Email creation: `createInviteLink` / `addMemberController`, including MCP email invitations; successful delivery only.
- Email resend: `reSendInvite`, reusing the invitation ID and original inviter.
- Public link GET/controller creation and POST rotation: `generatePublicInvite` / `getInviteFromProjectId`; link reuse is not a new send.
- Email and public-link acceptance: `members/invite`, after board membership creation.
- Existing teammate added by email: `sendInviteToAlreadyExistingMember`, with no fabricated invitation ID.
- Anyone task/board-share join: `members/share -> addExistingUserToProject`, attributing the sharer as inviter.
- MCP direct user-ID adds: `addExistingUserToProject`, attributing the authenticated caller as inviter. Both new-team-seat and existing-team-seat branches are covered, after transaction commit.
- Domain auto-join is not an invited membership and is excluded. Initial owner rows and agent memberships are excluded.

## Contract differences and rollout

The contract requires `subscription_started` after a positive **paid invoice**, not merely an active subscription at checkout/update. It adds `invoice_id`, `amount_paid`, `paid_at`, `is_first_subscription_for_user`, and the common attribution fields above. It has no `subscription_seats_changed` row; that event and seat-count/interval/discount properties follow the seat-tracking brief. There are no event-name conflicts. Existing Stripe billing controllers, billing writes and webhook response bodies are unchanged.

The production Stripe endpoint must deliver `invoice.paid` for subscription starts. The owning runner must verify that registration and live delivery; this helper does not call live Stripe/PostHog APIs. The broader tracking plan's automatic unresolved-mapping retry queue and attribution capture are not implemented by this analytics-only cutover; replay is supported without consuming failed/unmapped occurrences.

# Payment, login page, agent connection and delivery record (HTPR-7272)

Flag `htpr-7272-payment-login-agent-events` (https://app.hypertask.ai/admin/flags#flag-htpr-7272-payment-login-agent-events), default Owner + QA. Server events also need `isActivationEligible`. With the flag off for a user, nothing below changes for them: `agent_connected` keeps its per-credential key and captures stay inline.

| Event | Trigger and business ID | Additional properties |
| --- | --- | --- |
| `payment_succeeded` | Every verified `invoice.paid` with `status=paid`, positive `amount_paid` and a subscription, renewals included; invoice ID. Replays of the same invoice, under the same or a new Stripe event ID, send nothing more. A first invoice sends both `subscription_started` (HTPR-7268 flag) and `payment_succeeded`. The billed user comes from `team.stripe_customer_id`, never email; unmapped customers are skipped. | `stripe_event_id`, `stripe_customer_id`, `subscription_id`, `invoice_id`, `plan` (price ID of the invoice's subscription line, null if absent), `currency`, `amount_paid` (integer minor units), `paid_at` (ISO or null), `billing_reason`; `occurred_at` is the paid time |
| `signup_page_viewed` | Browser, once per `/login` navigation, only after PostHog loads with consent; a fresh `event_id` per navigation, also the envelope `uuid`. Signed-in viewers need the flag; signed-out viewers count only once the flag is at Everyone (they are in no audience before that). | `page_path=/login` (no query or fragment), `auth_state=authenticated\|anonymous`, `screen_mode=unknown` (login and signup share one screen), `source=web`, common fields null where unknown |
| `agent_connected` | First authenticated connection per durable connection: agent ID for agent credentials, key ID for management and `htk_` API keys, OAuth client ID for OAuth logins, `user_token:<transport>:<agent_type>` for plain CLI and user tokens. A renewed login or rotated credential for the same connection is not new. | `connection_id` (32-hex SHA-256 pseudonym of user and connection key), `agent_type=claude_code\|cursor\|codex\|hypertask_cli\|other`, `transport=mcp\|cli\|api`, `is_first`, legacy `client`, server common fields |

Browser `$identify` gets `event_id` (its envelope uuid) and `source=web` for signed-in users with the flag on, so browser and server identity operations can be told apart.

**Delivery record.** For flagged users every server occurrence from `captureAnalyticsOccurrence` (HTPR-7268 and HTPR-7272 events, plus activation events) is first written to the `AnalyticsOutbox` table with a unique business key (`<user id or business>:<marker>`), in the same transaction as the existing logs marker, then sent to PostHog after commit with the stored deterministic `uuid` and original timestamp. A failed send stays pending; `/api/cron/analytics-outbox` retries due rows every 5 minutes (backoff 1m, 5m, 30m, 2h, then 12h, at most 10 attempts) under a short lease so two runs never send the same row. Delivery pauses while the flag is off for that user and resumes when it is back on. Occurrences already marked before this change are never resent.

A credential already counted under the old per-credential key claims its durable connection silently when the flag reaches its user, so the rollout does not recount it. A `signup_page_viewed` queued before PostHog loads is dropped if the visitor signs in before that load, so very fast sign-ins can be undercounted.

Not covered here: unmapped Stripe customers are still skipped rather than queued (there is no user to attach the record to); first-touch attribution and consent fields remain HTPR-7269.

### Durable analytics intents

Saved tasks, boards, and columns record an ids-only analytics intent inside the save transaction. Onboarding and manifest boards enqueue immediately after their project is created; Stripe intents contain only the verified event id, and invoice acknowledgements wait for that insert. Post-response processing is a best-effort kick: the analytics outbox cron replays due intents before delivering occurrences, retries failed lookups, and removes processed intents after seven days. Stripe replay retrieves the event for analytics only and never reruns billing handlers.

# Versioned activation metric (HTPR-7293)

Flag `htpr-7293-activation-metric-v1` (https://app.hypertask.ai/admin/flags#flag-htpr-7293-activation-metric-v1), default Owner + QA, selects `definition_version=board_3_tasks_7d_v1` for `activation_completed` when `htpr-7284-activation-completed` is also enabled. With the new flag off, the existing unversioned live-task rule is unchanged. Guests remain excluded.

A user activates when one board they own (`Project.ownerId = User.id`, `Project.seeded = false`) was created in `[User.joinedAt, User.joinedAt + 7 days)` and three distinct task IDs on that same board have `Task.createdAt` in that window. Signup and the window start are inclusive; the end is exclusive. Tasks across boards never combine, and another owner's board never qualifies. Human- and agent-created tasks both count, with no creator filter.

This is a creation-fact metric, not a current-live-work count: later task soft-deletion, archival or status changes and later board archival/deletion do not disqualify the retained rows. Seed exclusion trusts `Project.seeded`, including the HTPR-7287 backfill. Hard-deleted task rows cannot be counted; no event history is reconstructed for them.

`activated_at` is the creation time of the third distinct task on the first qualifying board to reach three, not processing time. Order tasks by creation time, breaking ties by task ID; compare boards by their third-task time, then lower board ID, then task ID. `activation_task_ids` contains those three task IDs as strings in that order; `task_count=3`, `is_seeded=false`, `signup_at=User.joinedAt`, and `hours_since_signup` measures the threshold time. Common server board/workspace properties and `occurred_at` also use that threshold time.

The server-only `loadActivationFacts` / `computeActivationForUser` report computation can be rerun for any user, including after seven days; unchanged creation facts yield identical results regardless of input order or duplicate task rows. Live capture retains the existing triggering-time expiry check, skipping board/task queries when the triggering `occurredAt` is at or beyond signup + seven days. Durable task intents pass `Task.createdAt`, not processing time. Late delivery stores the threshold business time as outbox `occurredAt` and sends that original timestamp. The existing user-scoped `analytics:activation_completed` marker and `event_id=activation_completed:<userId>` still deduplicate once per user across both definitions: previously activated users are not emitted again or relabeled.
