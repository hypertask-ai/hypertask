# Feature flags

Add one client-safe file in `src/lib/flags/definitions/<flag-key>.ts`, exporting the key constant and a default definition. Type-only imports are allowed; runtime imports and side effects are not. Keep key, kind (if present), explicit defaultMode, shippedOn, description and related keys in that file. Include `releaseRisk: { risk, reason }` for flags first shipped from `RELEASE_RISK_REQUIRED_FROM` (2026-10-11). Use literal related keys so files stay independent. Add per-flag tests in their own test file, not shared key listings. A test that needs the flag registry stubs it with `stubFlags` from `tests/helpers/flags.ts`: it returns every real definition, takes per-key overrides such as `stubFlags({ [key]: { defaultMode: "EVERYONE" } })`, and throws on a key that is not registered. ESLint rejects a new hand-made `FEATURE_FLAG_DEFINITIONS` list or a hand mock of `@/lib/flags` in `tests/`, so a new flag never needs a test edit.

Do not edit shared keys, definitions or risk maps to add a flag. `scripts/generate-flag-index.mjs` validates and sorts the flag files and writes gitignored `index.generated.ts`. Never commit that index. Postinstall covers direct CI `tsc` after `npm ci`; npm prebuild, predev, pretypecheck, prelint and pretest hooks regenerate after local file additions. Next config also generates for direct Next builds/typegen, including installs using `--ignore-scripts`. The two isolated eval workflows explicitly generate after their `--ignore-scripts` installs, before direct Node tests. No manual step is needed. Direct `tsc` after an `--ignore-scripts` install must use `npm run typecheck`, not bypass its generator.

Existing keys.ts, definitions.ts, releaseRisk.ts and flags.ts imports remain supported. Agent run constants are re-exported from their flag files by agentRuns/model.ts. Non-flag reply guidance stays in keys.ts.

The release gate recognizes named imports and constant destructuring from awaited literal imports of flag readers and registered keys. Agent requests may return a flag read through an inline `withFeatureFlagSnapshot` callback imported from `@/lib/flags/modeCache`. The snapshot result must control runtime behavior; discarded results, fake readers or wrappers, shadowed bindings, and unused keys do not satisfy the gate.

New feature and improvement flags set `defaultMode: "EVERYONE"` in their definition file unless `releaseRisk.highRisk` is set (`money`, `access`, `data-deletion`, `customer-email`) or kind is `internal`. High-risk flags set `defaultMode: "OWNER_AND_QA"`; internal flags retain Owner + QA unless explicitly restricted further. Neither may default to Everyone. Bugfix flags inherit Everyone by kind unless high risk, which requires explicit Owner + QA. Existing flags keep their current mode (HTPR-7389). Infra tickets do not add a flag. An `internal` flag is test or agent plumbing: it never appears on `/admin/flags`, and agents read it through the MCP flags route instead.

New or changed `highRisk` metadata requires `harmEvidence: { harm, scenario }`. Match `money` with `charge`, `access` with `private-data-exposure` or `auth-bypass`, `data-deletion` with `permanent-deletion`, and `customer-email` with `customer-email`. Give a nonblank one-line scenario describing the concrete harm; reviewers must verify the claim. Unchanged legacy metadata remains valid. Owner-scoped agent actions and ordinary AI usage alone do not qualify. Safe nonvisual changes go to Everyone. Visual changes still need independent design QA before Everyone, and money still needs approval.

Only for Valentin's own explicit request, a new flag may instead use `defaultMode: "OWNER_ONLY"` with `releaseRisk.ownerRequest: { quote: "<his exact request>", ticketUrl: "<ticket link>" }`: the quote must be non-blank and the link must match `^https://app\.hypertask\.ai/detail/project-\d+/\d+$`. This exception permits only Owner only, not Owner + QA or Off, and does not replace required `releaseRisk.highRisk` metadata.

## API

`PATCH /api/mcp/flags` accepts `key`, `mode`, and one evidence field. For `ownerRequest`, use `source` (the scoped Hypertask comment URL), `quote` (1–1000 characters), and `requestedAt` (ISO datetime). Only the active owner-linked trusted lead with write access may submit it. The source must be unedited, accessible, and authored by the owner or trusted lead. The quote must occur in its visible text. Human source timestamps must equal the comment creation time; lead records may refer to an earlier request. Later owner withdrawals and superseding flag changes prevent replay. The audit stores the source and a SHA-256 quote hash, not the quote.

Existing approved `reason` links remain supported. Review receipts do not authorize switches. A `failure` record only moves Everyone to Owner + QA.

The trusted lead attests to the owner’s request. For lead-authored sources, the API cannot independently verify the original conversation or its provenance.
