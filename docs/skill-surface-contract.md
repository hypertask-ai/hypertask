# What `/skills` should do in Ctrl+J and comments

Recommendation for https://app.hypertask.ai/detail/project-15/7522.

**Status: internal proposal, not implemented.** Source reviewed at `38c69f9cb2e05e7efd0167edaaa8d0e434adec01`. Verification is code reading only: no tests, builds, typechecks, app servers, or browser demos were run. References below describe this checkout, not verified production behavior. Test references mean existing assertions inspected, not passing results.

## Recommendation in one sentence

A skill should shape the thing the person is writing: **a ticket draft in Ctrl+J, or their comment draft in comments**, with an explicit confirmation before publishing either; it should not silently become a standing instruction for a later chat. This extends the existing response-shaping resolver and comment Accept-to-editor path, but deliberately changes Ctrl+J's current send-and-save behavior (evidence: `src/app/api/ai/_lib/skills.ts:86–96`, `src/components/RTE/useTaskDetailEditorWriter.tsx:89–123`, `src/lib/ai/composeTask.ts:209–251`).

## 1. What the code does today

### A. Shared meaning of `/name`

- **A1 — Prompt template, not an action permission.** The resolver recognizes slash tokens, looks up enabled personal/accessible project skills, prefers the project version on a slug collision, removes recognized tokens, deduplicates skills, and appends their bodies as response-shaping instructions that must not override rules or tool-use policy. Unknown tokens remain unchanged. These are prompt instructions, not a mechanical guarantee about model compliance (`src/app/api/ai/_lib/skills.ts:14`, `src/app/api/ai/_lib/skills.ts:45–96`, `src/app/api/ai/_lib/skills.ts:99–125`).
- **A2 — `/deeper` is an example, not a verified built-in.** This resolver's built-in map contains only `/i` (Improve Readability); `/deeper` must resolve from an installed skill to have its intended effect. The comment tests supply a fixture body, not a production definition. No claim is made here about what the real `/deeper` body says (`src/app/api/ai/_lib/skills.ts:16–34`, `src/app/api/ai/_lib/skills.ts:48–65`, `tests/htpr-7480-comment-skill-run.test.cjs:205–212`).

### B. Ctrl+J new-ticket writer

- **B1 — The new-task path is a composer.** With `newTaskWindow`, the task-writer command routes to the compose tab. Compose sends the note to `/api/ai/task-writer` as `AiTaskWriter`, `requestKind: "compose-task"`, with board instructions. The server resolves skills from that prompt and adds their bodies to the writer's instructions; they therefore shape the generated ticket, not a separate chat answer (`src/components/commandDispatcher.ts:47–50`, `src/lib/ai/composeTask.ts:101–119`, `src/app/api/ai/_lib/taskWriterRun.ts:220–224`, `src/app/api/ai/_lib/taskWriterRun.ts:330–352`, `src/app/api/ai/_lib/taskWriterRun.ts:385–395`).
- **B2 — Today Send is also the save boundary.** Compose's send handler calls `createComposedTask`; that function generates the content and then calls the task-creation API without a second review/accept step. It can fill an existing empty target rather than always create a new ticket. If writing fails, it falls back to the original note and still saves. The result is consequently a saved ticket, not merely an unsaved AI draft (`src/components/Modals/commands/HTC/ComposeTaskWriter.tsx:219–259`, `src/lib/ai/composeTask.ts:198–209`, `src/lib/ai/composeTask.ts:224–262`).
- **B3 — The result lives on the ticket; chat receives a greeting.** After saving, Compose updates the board, opens sidebar chat, and navigates to the ticket. The handoff contains only `taskId` and generated greeting content; the greeting offers refinement and reports writer failure where applicable. Session history inserts that as an assistant message. There is no explicit handoff of the selected skill, its body, or the original invocation as active chat instructions in this path. This does not rule out ordinary influence from saved text/history (`src/components/Modals/commands/HTC/ComposeTaskWriter.tsx:292–306`, `src/lib/ai/composeTask.ts:34–46`, `src/hooks/MultiPages/AIChat/useSessionAndChatHistory.ts:533–546`, `src/lib/ai/chatStream/runStream.ts:199–211`).
- **B4 — A deeper research note is still a ticket-writing request.** When the existing draft-validation/research flag is enabled, the writer is instructed to describe research work, not perform the research or invent findings. A skill body is appended alongside that contract; it is not a separate research-execution mode (`src/app/api/ai/_lib/taskWriterRun.ts:348–363`, `src/lib/ai/prompts/definitions.ts:370–374`).

### C. Comments: routing is closer to the goal than input scoping

- **C1 — Picking a skill can run the local writer.** When both `htpr-7480-comment-skill-run` and `htpr-7393-comment-inline-ai` are enabled, choosing a skill in a new or edited comment removes only the slash-menu query and dispatches the intact `/name ` prompt to that editor. This evidence covers selecting a menu item, not automatic execution merely from typing `/name`. Without the execution conditions/target, the ordinary skill command inserts text; AI-chat picks also insert text. Both flag definitions default to Everyone, but that does **not** establish their current live modes (`src/components/RTE/Extensions/SlashCommands/CommandsList.tsx:37–44`, `src/components/RTE/Extensions/SlashCommands/CommandsList.tsx:74–84`, `src/lib/skills/slashSkills.ts:81–100`, `src/lib/flags/definitions/htpr-7480-comment-skill-run.ts:5–14`, `src/lib/flags/definitions/htpr-7393-comment-inline-ai.ts:5–14`).
- **C2 — It is not the generic inline editing component.** The event opens the targeted writer. For an auto-triggered slash skill in a comment, presentation explicitly selects the full `AITaskWriter` instead of `InlineDraftAiFloat`; it appears in the editor's popover. Ordinary comment AI remains local rather than opening the sidebar when the inline-comment flag is enabled (`src/components/RTE/useTaskDetailEditorEvents.tsx:30–32`, `src/components/RTE/useTaskDetailEditorEvents.tsx:123–145`, `src/components/RTE/taskDetailEditorPresentation.tsx:25–33`, `src/components/RTE/TaskDetailEditorPanels.tsx:123–146`).
- **C3 — The typed comment is not reliably the transformation input.** Presentation computes background content from editor HTML first and passes it with `currentTask` to the provider. However, the request hook prefers `currentTask.description_.content` over that background description, labels it `Original Description`, and sends the ticket title/description and task IDs. The slash pick supplies only `/name ` as the initial instruction. Thus the trace does not establish “transform this typed comment, use the ticket only as context”; a saved ticket body can displace the typed comment as the apparent source. The existing regression test explicitly expects the ticket body in this request (`src/components/RTE/taskDetailEditorPresentation.tsx:37–43`, `src/components/RTE/TaskDetailEditorPanels.tsx:132–145`, `src/components/PageComponents/TaskDetail/AI Task Writer/AITaskWriterWithProvider.tsx:37–47`, `src/hooks/MultiPages/AiWriter/useAiTaskWriter.ts:151–162`, `src/hooks/MultiPages/AiWriter/useAiTaskWriter.ts:198–223`, `tests/htpr-7480-comment-skill-run.test.cjs:190–212`).
- **C4 — Generation, acceptance, and posting are distinct here.** A skill can auto-generate a response, but the writer's Accept action calls `AISaveHandler`; in this comment path that handler replaces editor content and closes the writer, rather than posting a comment. Posting/saving the edited comment is a separate `sendComment`/`handleCallback` path that calls `handleSave` with comment content and mode. New-comment draft persistence can happen separately; “not posted” must not be described as “nothing persisted anywhere” (`src/components/PageComponents/TaskDetail/AI Task Writer/AITaskWriterContainer.tsx:319–345`, `src/components/RTE/useTaskDetailEditorWriter.tsx:89–123`, `src/components/RTE/useTaskDetailEditorSave.tsx:97–108`, `src/components/RTE/useTaskDetailEditorSave.tsx:145–164`, `src/components/RTE/Components/TiptapMainContainer.tsx:195–202`, `src/components/RTE/Components/TiptapMainContainer.tsx:353–364`, `src/components/RTE/useTaskDetailEditorDrafts.tsx:120–135`).
- **C5 — The generic inline writer has a different contract today.** `InlineDraftAiFloat` sends selected/draft `content` plus an instruction and ticket IDs to the forward-slash endpoint. Its result path can directly replace the editable draft; it also has proposal/freshness machinery. It is not evidence that all current inline operations wait for a separate Accept. Reusing its UI does not by itself implement skill expansion or the proposed review boundary (`src/components/RTE/Components/InlineDraftAiFloat.tsx:650–679`, `src/components/RTE/Components/InlineDraftAiFloat.tsx:720–729`, `src/components/RTE/Components/InlineDraftAiFloat.tsx:783–810`, `src/components/RTE/Components/InlineDraftAiFloat.tsx:962–976`, `src/components/RTE/Components/inlineDraftAi.ts:19–38`).

### D. Other call sites: do not confuse them with draft editing

- **D1 — Sidebar/Agent Chat resolves skills per incoming request.** It resolves the current message with the user's project scope, adds skill instructions to the model turn, and separately loads the current ticket as context. It also builds tools, so this is a different action surface from a comment-draft writer. This trace contains no standing skill setting inherited from Ctrl+J (`src/app/api/ai/_lib/chatSkillResolution.ts:1–8`, `src/lib/ai/chatStream/runStream.ts:199–211`, `src/lib/ai/chatStream/modelTurn.ts:41–64`).
- **D2 — MCP task-writer is draft-only, but chat task creation is not.** `/api/mcp/ai/task-writer` maps `prompt` to the same preparation/generation path and returns HTML, title, properties, and resolved skill names. That path returns a draft without creating the ticket. In contrast, the chat `createTask` tool's writer-enabled brief path calls `generateTaskWriterDraft` and then `createTask`; its successful execution really saves. Do not generalize the MCP draft response into a universal preview-before-save guarantee (`src/app/api/mcp/ai/task-writer/route.ts:49–79`, `src/app/api/ai/_lib/taskWriterDraft.ts:24–44`, `src/app/api/ai/_lib/taskWriterDraft.ts:65–76`, `src/lib/ai/tools/createTask.ts:175–224`).
- **D3 — MCP skill management manages templates, not a comment-writing session.** The skill service exposes list/get/create/update/delete/import through `/mcp/skills`; these calls are separate from resolving a template into a writer prompt (`src/lib/mcp-server/lib/services/skill.service.ts:69–75`, `src/lib/mcp-server/lib/services/skill.service.ts:99–110`, `src/lib/mcp-server/lib/services/skill.service.ts:140–145`, `src/lib/mcp-server/lib/services/skill.service.ts:177–182`, `src/lib/mcp-server/lib/services/skill.service.ts:211–216`, `src/lib/mcp-server/lib/services/skill.service.ts:248–253`).
- **D4 — HyperAI mentions are an important exception.** The mention route also resolves skills and generates a response, but then posts a bot comment through `createCommentService`. A skill in that separate flow is not the same operation as picking a skill to transform an unsent human comment. The proposed draft contract must not accidentally invoke the mention/post pipeline (`src/app/api/ai/hyper-mentioned/route.ts:238–242`, `src/app/api/ai/hyper-mentioned/route.ts:350–375`, `src/app/api/ai/hyper-mentioned/route.ts:417–430`).

### Scope and failure rules

- **Keep source and context separate.** Proposed comment input should explicitly distinguish the comment to transform from the ticket background and skill instructions. Recognize skill invocations in the person's instruction/comment source, not incidental `/names` in the background ticket. The current resolver scans the entire supplied prompt, while the hook embeds the ticket description there; this is another reason to separate these roles (`src/app/api/ai/_lib/skills.ts:45–48`, `src/hooks/MultiPages/AiWriter/useAiTaskWriter.ts:198–205`).
- **Do not silently turn an empty comment into “rewrite the ticket.”** For `/deeper` alone, ask the person for comment text or a comment-writing instruction before generating; an explicit “draft a reply about this ticket” instruction may use ticket context. This is a proposed safeguard against C3's fallback, not an existing validation (`src/hooks/MultiPages/AiWriter/useAiTaskWriter.ts:151–154`, `src/components/RTE/Extensions/SlashCommands/CommandsList.tsx:77–80`).
- **Keep skills subordinate to the surface.** In Ctrl+J, `/deeper` should deepen the draft's framing, questions, or acceptance criteria as its installed instructions request, not claim to have completed the work. In comments it should transform the supplied comment, not rewrite the title/body. Retain the resolver's rule/tool-policy hierarchy and the ticket writer's research constraint (`src/app/api/ai/_lib/skills.ts:86–94`, `src/lib/ai/prompts/definitions.ts:370–374`).
- **Failure is not confirmation.** Recommend keeping the original note/comment and showing a recoverable error, without auto-creating a fallback ticket or posting anything. This changes Ctrl+J's raw-note save fallback; preserve the comment editor's separate publication action (`src/lib/ai/composeTask.ts:198–209`, `src/components/RTE/useTaskDetailEditorSave.tsx:97–108`).
- **Never overwrite newer typing on acceptance.** Bind the proposal to its originating editor/ticket and source revision; if the person edits meanwhile, preserve both texts and require regeneration or explicit reconciliation. Reuse the existing freshness approach rather than assuming the full writer already has it (`src/components/RTE/Components/InlineDraftAiFloat.tsx:962–976`, `src/components/RTE/useTaskDetailEditorWriter.tsx:89–95`).

### Inline writer and sidebar: one target, not two competing destinations

**Recommendation:** reuse the existing comment-local writer entry point and editor; converge skill selection and ordinary inline writing on one review model. Do not add a second skill-specific sidebar or a second comment composer. The current skill route uses the full writer specifically to preserve its initial prompt, whereas the generic inline route sends content/instruction directly; integrating those routes needs explicit source separation and review behavior, not just a component swap (`src/components/RTE/taskDetailEditorPresentation.tsx:25–33`, `tests/htpr-7480-comment-skill-run.test.cjs:146–165`, `src/components/RTE/Components/InlineDraftAiFloat.tsx:720–729`, `src/components/RTE/Components/InlineDraftAiFloat.tsx:783–810`).

Keep the sidebar for an explicit conversation or **Edit ticket with AI** action, not the default destination of a comment skill. That existing action opens the sidebar and starts a session for ticket editing, a different target (`src/hooks/MultiPages/AIChat/useCommentToAiChat.ts:129–141`). If a later design offers “continue in chat,” make it opt-in, visibly name the target as “comment draft,” preserve the unsent original, and return any chosen result to the same inline review/Send boundary. This is a proposal, not a currently evidenced handoff; existing comment routing deliberately suppresses the ticket-edit sidebar path (`src/components/RTE/useTaskDetailEditorEvents.tsx:30–32`, `src/components/RTE/useTaskDetailEditorEvents.tsx:123–145`).

## 4. Evidence blockers before claiming production behavior

- **Production prompt logs unavailable/not inspected.** No captured production model request proves which template body, prompt version, context, or live flag modes actually applied. Source construction and mocked test fixtures are the available evidence; they cannot substitute for those logs (`src/app/api/ai/_lib/taskWriterRun.ts:220–224`, `src/app/api/ai/_lib/taskWriterRun.ts:385–395`, `tests/htpr-7480-comment-skill-run.test.cjs:205–212`). Do not retrieve credentials or raw sensitive prompt content to fill this gap.
- **Live demos unavailable/not performed under this task's constraints.** No recording or observed production click-through shows `/deeper` in Ctrl+J, a new/edited comment, or the follow-up chat. Both flag files provide defaults, not observed deployment state (`src/lib/flags/definitions/htpr-7480-comment-skill-run.ts:5–14`, `src/lib/flags/definitions/htpr-7393-comment-inline-ai.ts:5–14`).
- These are blockers to a **verified live-behavior claim**, not to choosing this contract. Before implementing or declaring the experience correct, obtain authorized, redacted prompt-shape evidence and demos of both confirmation boundaries, using a known installed skill; do not infer either from the fixture named `/deeper` (`tests/htpr-7480-comment-skill-run.test.cjs:205–212`).

## 5. Product-owner decisions

Recommended answer: **Yes** to each; these are approval questions, not existing behavior claims.

1. Should a skill in Ctrl+J shape a ticket draft that the person reviews before creating or filling the ticket?
2. Should a skill in comments transform only the person's comment, using the ticket as background without changing it?
3. Should the person accept the comment draft first and then use the normal Send or Save action to publish it?
4. Should skills apply only where invoked, with no automatic carryover into follow-up chat?
5. Should comment skills stay in the inline writer, with the sidebar used only when the person explicitly chooses a conversation?
