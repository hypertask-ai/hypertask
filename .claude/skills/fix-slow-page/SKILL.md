# fix-slow-page

Use at `/ship`'s fix step for a slow board, inbox or task view. This is the how-to, not another ship map. Board writes go through `vcc`. Product Bot's speed facet measures read-only and reports one ticket; this developer session fixes it.

**Flag rule (matches `fix-bug` and `INDEX.md`):** speed work with identical intended behavior is a bug fix, no flag, even when the improvement is visible. A behavior change is a feature: load `ship-feature-behind-flag`, not a disguised flag-free speed fix. Existing Merge Rules row 4 still governs speed rollout: one speed change at a time, never automatically switched on in working hours. No flag does not bypass review, deployment or QA gates.

## Steps

1. **Reproduce before editing.** Resolve the shared company pack from `$COMPANY_SKILLS_DIR` or `~/projects/company-skills`, read `skills/speed-check/SKILL.md`, then its `measure.md` at this step. Use only the QA-normal saved login (user 2343) and QA Sandbox fixture, never owner/customer credentials. Run at least five cold and five warm samples for the ticket's surface and profile; keep the full before summary, per-run JSON, release/commit, exact command and conditions. The board-to-task path is distinct from direct task load. If the ticket cannot reproduce, say Can't verify and stop rather than inventing a cause.
2. **Find the measured cause.** Load speed-check's `trace.md`, capture one Chrome performance trace through CDP and one Playwright trace. Then load `diagnose.md`; open `tools.md` only for the specialist instrument needed. Follow the owning route, component, query key, server query, hydration and cache invalidation. Use React Scan or bundle analysis in local/staging only. No production k6 load. Raw traces may contain auth headers: inspect privately and share only sanitized excerpts.
3. **Write a failing regression test.** Load `fix-bug` for its test and security rules; UI work first loads `reuse-existing-ui`. Exercise the real implementation or boundary, not a copied function or source-text check. Capture the unnecessary call, re-render, slow query or bundle growth. Preserve user-scoped caches, permissions, fresh data, focus, keyboard access, loading/error states and mobile interactions.
4. **Make the smallest fix.** Change only the measured owner. No unrelated refactor, new optimistic shell masquerading as visible content, broad dependency rewrite or flag for unchanged behavior. If behavior must change, stop this path and take the feature path. Run relevant tests and a fresh typecheck on the CI Node major; follow the existing app performance budget and speed evidence gate when they apply.
5. **Prove before and after on the ticket.** Use the exact same browser, viewport, network/CPU, fixture, cache states, sample counts and observation protocol. Measure the fixed preview/local build only if it can safely use the QA fixture and the same read-only guard. The shared script deliberately targets live production; never edit its BASE to a preview sharing the live database. For a pre-merge preview proof, use the app's approved performance harness with a configured target and document any environment difference. Do not claim preview-versus-production numbers are controlled proof. Once deployed, re-run speed-check on live under the same conditions. A two-sample smoke is not regression proof.
6. **Post the evidence, not “feels faster”.** Via `vcc`, put a table on the ticket: surface/profile/cache, before and after median/p90 content-visible ms, navigation LCP ms (n/a for SPA task-from-board), compressed downloaded JS bytes, sample counts and percent delta. Include safe artifact links, exact commands, commit/deployment identity, API call-count changes and cause. Keep every slow sample; compare to the original before summary and approved budgets, not to a newly seeded after baseline. If after is not actually better, fix or explain the result before proceeding.
7. **Return to `/ship`.** Load `simplify-before-pr`; UI proof uses `design-compliance` and `verify-on-phone`, user-visible changes use `update-docs`. Preserve the existing `performance/evidence` schema and CI proof requirements for a speed code change. Review speed rollout constraints before merging. After production deploy succeeds, run live speed-check and `verify-qa` and add both results to the ticket's QA report. Faster is not enough if behavior regressed. Never merge or close solely because a lab score passed.

The shared check is read-only by design and blocks app writes and unknown API reads. Auth/selector/tool failures are Can't verify, not speed regressions. Fix a proven measurement lesson in its owning speed-check detail and test using `improve-skill.md`; never relax budgets or safety to turn the run green.
