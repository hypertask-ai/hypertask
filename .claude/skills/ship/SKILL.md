3a. **Deeper, not bigger** (Valentin, 2026-10-17, YPER4-435: "it's good for agents to consider if they can execute the task in a better, more professional way"). If something live already covers the job, the ticket is to fix or reuse that, not to add a second one; prove the new piece does not duplicate it (for example one test event produces exactly one ticket).

## Several tickets

1. **Claim all first.** Do steps 0 to 2 for every ticket before any work: read each, claim each (comment, `--self`, In Progress). Name the session after the first ticket plus "+N more".
2. **One checklist.** `ship-gates HTPR-6857 HTPR-6856 HTPR-6855` writes every ticket's gates into the same ledger. The unlazy stop hook keeps the session going until all of them are met.

4. **A ticket you cannot finish** (taken by someone else, needs Valentin's answer): give it its normal handoff on the ticket, add `ABANDON: <gate id> <reason>` for its open gates, and move on to the next.

## Tickets assigned to a runner on the board

Assigning a ticket to a runner's agent is an equal way to hand it work next to chat (YPER4-244). A user timer `runner-pickup@<n>.timer` (every 3 minutes, one board read, exponential backoff on errors, no GitHub) writes `~/.local/state/runner-inbox/runner-<n>.json` with that runner's assigned tickets that are not yet claimed (not In Progress, AI Review, QA, Valentin Review or Done; changed in the last 7 days). A runner still not working a queued ticket after one tick gets one agent activity line on it saying it is queued. A hook (`.claude/hooks/runner-inbox-stop.sh`, only for sessions named `RUNNER <n>` with no unmet unlazy gate) delivers the oldest queued ticket once, at the end of a turn or on the next prompt: run `/ship <TICKET>` on it. Install after merge, as that runner: `.claude/skills/ship/scripts/runner-pickup install <n>`.

The `runner-selfupdate.timer` reinstalls runner scripts, the hook and webhook within 5 minutes after the production copy changes. Failed installs keep the old version and alert HT Product Lead. Set it up once with `.claude/skills/ship/scripts/runner-selfupdate install`.

Board events reach a live runner too (YPER4-256): the receiver `runner-webhook` (front door on 127.0.0.1:8793 for the hooks.hypertask.ai tunnel; routes `/webhook/runner-<n>`, `/webhook/ht-product-lead` (`/webhook/infra-manager` remains an alias with the same `infra-manager` signing config and inbox slot) and `/webhook/speed-runner`, everything else proxied to the legacy agent-events receiver on 8795; signed, one secret file per runner in `~/.config/hypertask-agents/runner-webhooks/`; install with `runner-pickup install-webhook`) hands human comments, mentions, assignments and Agent Chat messages to the session named `RUNNER <n>` (`runner-deliver`; HT Product Lead if the runner is not live, else queued), and each pickup tick re-reads the agent inbox as a backstop. Since YPER4-284 nothing is typed into a session that runs the events hook: the event goes to `~/.local/state/runner-inbox/<slot>.events.jsonl` and the same hook hands it over as its own message (between tool calls, at turn end, or by waking an idle session through `asyncRewake`). Typing through tmux remains only for a session without the hook (slot not in `events-hook.enabled`), logged to `typing-fallback.log`. A runner answers a chat with `runner-chat-reply <n> <session-id> "<text>"`.

## Rules that hold the whole session

- **PR name (Valentin, 2026-10-01).** Exactly `HTPR-NNNN [TYPE] <short description>`: a ticket that exists on the board, then a type the repo title check accepts: `[BUGFIX]`, `[FEATURE]`, `[IMPROVE]`, `[INFRA]` (also `[SPEED]`, `[QA]`, `[CLI/MCP/AI]`, `[DASH]`, `[BOARD]`, `[COST]`, `[PLAN]`, `[FEEDBACK]`, `[REFACTOR]`). Example: `HTPR-6370 [BUGFIX] Chip markers, readable summary, Escape and refocus in search picker`. Wrong name: `gh pr edit <n> --title "..."`, or create the missing ticket via `vcc` and retitle.
- **Flag removals and ux-signoff (Infra Manager, 2026-10-12, YPER4-323).** ux-signoff stays advisory (not required). A flag-removal PR may merge with a red ux-signoff when it changes nothing visible, provided the PR description says so in one line. Never retitle a PR to clear a check.
- **Hard block.** A Claude Code hook (`ship-check guard`) refuses `gh pr merge` on a wrongly named PR or one whose ticket does not exist, and refuses `vcc task move HTPR-NNNN --section "Done"` until the PR is merged, the Production deployment is success, and `~/.local/state/vcc-evidence/HTPR-NNNN/proof.md` follows the verify-qa contract with screenshots. Merge is also refused while the PR's own ci-tests is not green on its head, or passed only before production went red (rerun it), naming the failing test and whether production is red too. When it blocks you, do the missing step; never work around it. Infra tickets (YPER4, HYFA) need the merge and the deploy before Done; app tickets also need the proof. CLI work: prefix `ship-gates` and the `ship-check` commands with `SHIP_REPO=hypertask-ai/cli SHIP_BASE=main SHIP_CHECKOUT=$HOME/projects/hypertask-cli-zig`; `ship-gates` writes those settings into every checklist check, so the checks read the CLI repo. Verify-repo work (`hypertask-ai/verify`, the nightly and explore checkers): prefix `ship-gates`, every `ship-check` and the `vcc task move <TICKET> --section "Done"` command itself with `SHIP_REPO=hypertask-ai/verify SHIP_BASE=app-suite SHIP_CHECKOUT=$HOME/projects/hypertask-verify-app` (base `app-suite`, not the stale `master`; the Done guard reads the repo only from that command's own prefix, and a hand-edited checklist check makes `ship-gates` refuse to run). Deployed there means a GitHub release on the merge commit (`gh release create <ticket in lowercase> -R hypertask-ai/verify --target <merge sha> --latest`), then `git -C $HOME/projects/hypertask-verify-app pull --ff-only` so the nightly runs it. Other repos use their own `SHIP_REPO`, `SHIP_BASE` and `SHIP_CHECKOUT`; for a release-less Cloudflare worker repo, also set `SHIP_WORKER=workers/docs-agent` (relative to the checkout), whose `wrangler.toml` must declare a top-level `name` (`[A-Za-z0-9_-]+`) and `account_id` (32 lowercase hex characters); only those data are read, and pinned `wrangler@3.114.17` runs from the empty `${XDG_CACHE_HOME:-$HOME/.cache}/ship-check-wrangler` directory outside checkouts and local npm packages. `ship-gates` persists `SHIP_WORKER`; deployed checks require one active version at 100% whose message is the full merge SHA or whose tag is its first 12 characters. Tests: `.claude/skills/ship/scripts/ship-check.test.sh`. Codex has no hook: run the same `ship-check` commands yourself before merge and before Done.
