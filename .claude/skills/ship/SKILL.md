# Ship

Valentin types only `/ship <ticket>` at the start of a session (2026-10-01: "i only type /ship at the beginning of a session and it does all of these automatically, most importantly gives itself and its sub agents a ledger"). This session does the whole ticket itself.

This file is the map. It does not hold the how-to. At each step, load the skill named there and follow it. Load a skill when you reach its step, not before (progressive disclosure: Valentin, 2026-10-01).

## Before anything else

- **No ticket given: board check first** (Valentin, 2026-10-01). Run `~/.agents/skills/ship/scripts/board-check` (read only). It walks open PRs, then AI Review, QA and In Progress, and lists every ticket with no sign of life for 6 hours. Show Valentin each line as the full ticket title with its full URL and the suggested action, and ask per ticket: take it, move it back, or drop it. "move back to Bugs" or "move back to Todo" is only a suggestion; when the ticket is not clearly a bug or a feature, ask where it goes. Do nothing to a listed ticket until he answers. Then pick by your name (`~/.agents/skills/ship/scripts/ship-identity`; Valentin, 2026-10-03: "runner 1 and 2 are neutral"): a BUG RUNNER picks the top free bug, a SPEED RUNNER the top free speed ticket, and any other runner (RUNNER 1, RUNNER 2) the top free ticket of any kind (Valentin, 2026-10-03: "it should work for all runners speed, bug, neutral... and any type of ticket"). Everything after this point is the same for every runner and every ticket type. Then go to step 0.

0. **Session title and link** (Valentin, 2026-10-01). As soon as you know the ticket, whether he gave it or you picked it ("pick a ticket from board 15"), read it (`hypertask tasks get HTPR-NNNN`) and start your reply with the full ticket URL (`https://app.hypertask.ai/detail/project-<projectId>/<number>`). Open that URL in his zsb pane. Only if the session has no name yet (`~/.agents/skills/ship/scripts/ship-identity` prints Valentins Claude Code and Valentin never renamed it), put `/rename HTPR-NNNN | <exact ticket title>` above the URL; never rename a session he named (Valentin, 2026-10-02). In Codex, print it as the suggested thread name.
1. **Identity.** Every board write (claim, comment, move, assign, attachment) goes through the `vcc` command, and only that. `vcc` writes as the identity `~/.agents/skills/ship/scripts/ship-identity` prints: the session's own name when Valentin put a token for that name in `~/.config/hypertask-agents/credentials/sessions/`, else Valentins Claude Code (Valentin, 2026-10-02). It survives /clear because the session name does. Never pick an identity yourself, never the plain `hypertask` CLI for writes (Valentin's own token; reads only). Every comment's closing `Next:` paragraph ends with this session's exact resume command (`claude --resume <full $CLAUDE_CODE_SESSION_ID>`, or `codex resume <id>`). Read the ticket back after each write. If `vcc` fails, stop and tell Valentin in one line.
2. **Claim first, before anything else** (Valentin, 2026-10-02: "claim and move the ticket FIRST so its right away out of the bug column"). Right after reading the ticket, and before you examine the ticket, write the checklist or start a helper: unless the ticket is already taken (the claim rule in the board check), post the "Claimed." comment, add your own agent (`vcc task assign HTPR-NNNN --self`), move it to **In Progress** with `vcc task move`, and read it back. Only then start examining.
3. **Checklist.** Load `unlazy`, then run `~/.agents/skills/ship/scripts/ship-gates HTPR-NNNN`. It writes and approves only its fixed, read-only checks in `$PWD/.unlazy/s-<first 8 chars of the session id>/GATES.md`, binding the full session id in `session`. More tickets append to that ledger. Put extra outcomes in the same scope's `gates/extra.md`; inspect and approve them separately. Run `node ~/.agents/skills/unlazy/scripts/gate-check.mjs <ledger>` after every map step and before any "done" report; quote its met, unmet and abandoned counts to Valentin. The installed unlazy Stop hook blocks ending a turn while gates are unmet. If you must wait for Valentin (a `Question:` comment or Valentin Review), keep each remaining gate and append `ABANDON: <id> waiting for Valentin: <reason>` at column 1 of its ledger. Recheck, report the abandonment and required handoff, and stop without claiming completion. A `ship-check duplicate` ticket uses these same gates.
4. **Helpers are Codex sub-sessions via hax, each with its own ledger** (Valentin, 2026-10-03). All delegated execution (coding, tests, research, reading big files) must go to Codex: `hax --provider=codex --model=gpt-6.1-sol --effort=high --no-session -p "<prompt>"`, in the background, one hax run per independent piece. Never the Agent tool or Claude subagents for delegated work, never `--provider=zai` or OpenRouter. The runner's own Claude session only plans, judges, reviews and talks to Valentin. Every helper prompt starts with: "Use the unlazy skill (~/.agents/skills/unlazy/SKILL.md): write GATES.md first and prove every gate before your final answer." Re-run its gates yourself (`gate-check.mjs --reverify`) before you trust it.
5. **Voice.** Load `pospeak` (chains `unslop` and `i-have-adhd`) for every reply to Valentin.

## Several tickets

Valentin, 2026-10-03: "/ship 6857, 6856, 6855 ... claim all of these tasks right away so other sessions know you are working on them". A bare number means `HTPR-`.

1. **Claim all first.** Do steps 0 to 2 for every ticket before any work: read each, claim each (comment, `--self`, In Progress). Name the session after the first ticket plus "+N more".
2. **One checklist.** `ship-gates HTPR-6857 HTPR-6856 HTPR-6855` writes every ticket's gates into the same ledger. The unlazy stop hook keeps the session going until all of them are met.
3. **One at a time, in the order given.** Each ticket gets its own branch, pull request, QA and Done, as if shipped alone.
4. **A ticket you cannot finish** (taken by someone else, needs Valentin's answer): give it its normal handoff on the ticket, add `ABANDON: <gate id> <reason>` for its open gates, and move on to the next.

## Local premerge board click

Use `scripts/premerge-local.sh up` as a managed background task from the PR worktree to build and serve the CI browser-smoke app with disposable Docker services and a seeded signed-in board. It prints URLs, a Playwright storage-state path and the `premerge.md` starting lines. Follow `.claude/skills/verify-qa/SKILL.md` "Disposable local PR build" to capture the changed-path click and recording, confirming the snapshot matches live flag modes. Keep the task alive during QA, then finish with `scripts/premerge-local.sh down` from another command. Exiting or interrupting the task also stops its servers and containers. This needs Docker, Node 24 and no `.env` files; it never uses a production database and does not replace live QA after deploy.

## Rules that hold the whole session

- **PR name (Valentin, 2026-10-01).** Exactly `HTPR-NNNN [TYPE] <short description>`: a ticket that exists on the board, then a type the repo title check accepts: `[BUGFIX]`, `[FEATURE]`, `[IMPROVE]`, `[INFRA]` (also `[SPEED]`, `[QA]`, `[CLI/MCP/AI]`, `[DASH]`, `[BOARD]`, `[COST]`, `[PLAN]`, `[FEEDBACK]`, `[REFACTOR]`). Example: `HTPR-6370 [BUGFIX] Chip markers, readable summary, Escape and refocus in search picker`. Wrong name: `gh pr edit <n> --title "..."`, or create the missing ticket via `vcc` and retitle.
- **Hard block.** A Claude Code hook (`ship-check guard`) refuses `gh pr merge` on a wrongly named PR or one whose ticket does not exist, and refuses `vcc task move HTPR-NNNN --section "Done"` until the PR is merged, the Production deployment is success, and `~/.local/state/vcc-evidence/HTPR-NNNN/proof.md` follows the verify-qa contract with screenshots. When it blocks you, do the missing step; never work around it. Infra tickets (YPER4, HYFA) need the merge and the deploy before Done; app tickets also need the proof. CLI work: prefix `ship-gates` and the `ship-check` commands with `SHIP_REPO=hypertask-ai/cli SHIP_BASE=main SHIP_CHECKOUT=$HOME/projects/hypertask-cli-zig`; `ship-gates` writes those settings into every checklist check, so the checks read the CLI repo. Tests: `.claude/skills/ship/scripts/ship-check.test.sh`. Codex has no hook: run the same `ship-check` commands yourself before merge and before Done.
- When live QA FAILs on code behind a flag, switch that flag Off on /admin/flags first (seconds, no deploy), then repair. Only Valentin's login can open that page: a runner sends the flag key and the failure to the INFRA MANAGER session with SendMessage at once, and it switches the flag Off. A revert PR is the second step, not the first. (Valentin, 2026-10-03)
- Any change to code inside a flag that is already on for Everyone, whatever its PR type ([BUGFIX] included), needs one recorded browser click-through of the changed path on a real board before merge, on the preview or locally against the PR build, with the live flag states. Record commit, account and flag state in ~/.local/state/vcc-evidence/<TICKET>/premerge.md.
- GitHub requires `premerge-evidence` on the current PR head, including merges inside scripts or background loops. `ship-check pr` and the merge guard publish it automatically. After recording a click, run `.claude/skills/ship/scripts/ship-check premerge-status <pr number>` to refresh it immediately. Registry defaults are not proof that a flag is unreleased when live modes cannot be read.
- The VPS user timer `premerge-evidence.timer` reconciles open production PRs every two minutes. Each sweep fetches the current `ship-check` from GitHub's `production` branch and atomically saves an executable in its state folder. Changed rules, records or recordings trigger an immediate recheck; unchanged results refresh every ten minutes for live flag changes or transient errors. A failed rules fetch never runs a stale copy: it turns every passing status red until the next good sweep. Install or update the standalone poster with `python3 .claude/skills/ship/scripts/premerge-evidence.py --install`; it survives worktree cleanup. Check `systemctl --user list-timers premerge-evidence.timer` and `journalctl --user -u premerge-evidence.service`. Seed statuses for all open PRs before making the context required.
- **Document every QA run** (Valentin, 2026-10-01: "tells you to also document your QA run"). Each run, pass or fail:
  - Before testing, write the checklist from the acceptance criteria and the feature-map page. After testing, mark each line PASS, FAIL or UNREACHABLE with its evidence file; a FAIL line says the exact steps and what happened.
  - Save the run in `~/.local/state/vcc-evidence/HTPR-NNNN/<YYYY-MM-DD>-qa-run-<n>/`: checklist, screenshots (desktop 1440x900 and phone 390x844, all four themes (Porcelain, Graphite, AMOLED, Dia; see verify-qa) when UI changed), a short video of the main path, which accounts were used (user id and role, never credentials). Keep `HTPR-NNNN/proof.md` (verify-qa contract) pointing at the latest run.
  - Build one self-contained HTML report (results plus key screenshots inline, ticket titles as full links) and put it **on the ticket as a page**, never on hypertask.app (Valentin, 2026-10-02: "tickets have sub pages why don't we put it in there"): `vcc pages create --task HTPR-NNNN --title "QA run <n> (<YYYY-MM-DD>)" --canvas --markdown-file <report.html>`. Its link is `https://app.hypertask.ai/page/<publicId>` (`hypertask pages get <id> --json`). Open it in his zsb pane. The video does not go in the page; attach it to the QA comment.
  - One QA comment on the ticket via `vcc`: verdict in the bold first sentence, PASS and FAIL lines in plain words, key screenshots and video with `--attach`, the report page link.
  - Tell him in chat: verdict first, the report page link, anything not tested. Example: the QA run 1 page on https://app.hypertask.ai/detail/project-15/6630
- **Move the ticket as the work moves** (Valentin, 2026-10-01). Via `vcc task move HTPR-NNNN --section "In Progress"` (or the column named below), then read it back:
  - **In Progress** when you claim and whenever you go back to fixing.
  - **AI Review** as soon as the PR is open, until merged.
  - **Done** once the merge is live and QA passed with evidence on the ticket.
  - **Valentin Review** only for a real decision only he can make (a wireframe he asked for, money, login and access, security, something nobody can undo), with one `Question:` comment. Abandon the remaining gates with that waiting reason per step 3, and say so.
  - **Never Valentin Review to ask about a flag** (Valentin, 2026-10-03: "you cannot put stuff in Valentin review to ask me to turn on the flag. I decide when to turn on the flag"). A flagged ticket goes to **Done** once its live QA passes on Owner + QA. Do not ask him to switch the flag on, in a comment or in chat; he switches it on the flags page when he wants.
  Follow-up work becomes its own ticket.
- **The ticket tells the whole story; comments are for people** (Valentin, 2026-10-01: "comments are for humans and agent chatter goes into the agent chatter").
  - **Comments** only when you speak to a person: the claim, a `Question:` for Valentin, the QA verdict. Plain language (pospeak), bold first sentence, never notes to yourself.
  - **Agent activity** gets everything else: plans, progress, retries, test runs. Write it with `vcc activity add HTPR-NNNN "<one line>"` at every step of the map (claimed, fix done, PR opened, checks green, merged, deployed, QA done) and at least every 2 hours while you work. This is your heartbeat.
  - **Claim** = add your agent with `vcc task assign HTPR-NNNN --self`, plus a "Claimed." comment whose `Next:` paragraph carries your resume command.
  - **Taken or free:** a ticket is taken when it has such a claim and the claiming agent's newest agent activity (`vcc activity last HTPR-NNNN`) is under 6 hours old. Older than 6 hours: the claim is stale, and the board check lists the ticket for Valentin.
- **Already fixed by another ticket: the duplicate path** (Valentin, 2026-10-01). When your ticket (bug, feature or improvement) was already done by another ticket's merged PR, ship nothing and throw away any duplicate fix. Then:
  1. `~/.agents/skills/ship/scripts/ship-check duplicate HTPR-NNNN HTPR-MMMM <that PR number>` (HTPR-MMMM is the ticket that fixed it). From then on the merged, deployed and proof gates check that PR.
  2. Record the branch you made, so cleanup can check it: `ship-check branch HTPR-NNNN <your branch>`, or `ship-check branch HTPR-NNNN none` if you made none.
  3. Prove on the live site the bug is gone or the feature works, exactly like any QA run (repo `verify-qa`, `proof.md` with the fixing PR's merge sha).
  4. One comment via `vcc`: bold first sentence "Already fixed by <full title of HTPR-MMMM as a link>.", what you checked live, the evidence attached. Then `vcc task move HTPR-NNNN --section "Done"`.
  If it is only partly fixed, it is not a duplicate: keep working it as a normal ticket.
- **Archived is not gone** (Valentin, 2026-10-02: "agents have to learn about the archive pls that is not good otherwise"). Archiving hides a ticket from the board and keeps it: `hypertask tasks get` still returns it with `"status":"Archive"`; the trash is `"status":"Deleted"`.
  - **Searching** for an existing ticket, a duplicate or the ticket that already did your work: search all three, `ht GET "/mcp/tasks?status=Normal&search=<words>"`, then `status=Archive`, then `status=Deleted`. Moving a ticket to another board gives it a new number and the old link stops working, so a missing number can be the same ticket under a new number: search its title (from the old link's comments, PR or session logs) in all three. A ticket is gone only when the title search and `tasks get` both find nothing; then say "deleted, not in the archive", never just "not on the board".
  - **Given an archived ticket:** say so in your first reply, with the column it was archived in. Archived in Done means finished: check live whether it still works (a bug is not back, a feature is still there) before doing anything. Archived in any other column can be unfinished work: bring it back with `vcc task update <TICKET> --status Normal`, read it back, then work it like any ticket.
- **Clean up after yourself** (Valentin, 2026-10-01). Once the ticket is Done, load `clean-up` and remove only the worktree and branch this session created.
- **Finish with cleanup proof and the next ticket** (Valentin, 2026-10-03: "print out the clean up confirmation of the worktree and branch ... then also make the agent suggest the next free unclaimed task"). Once QA passed, the ticket is Done and `ship-check cleaned` printed `cleaned ok`, end your report to Valentin with:
  1. One line naming the removed worktree path and branch, plus `cleaned ok`.
  2. The next ticket you suggest: full title and full URL, picked the same way as "No ticket given" (your runner type, top free ticket). Before you name it, read it fresh: it must not be Done, claimed ("Claimed." comment or an agent assigned), or in Valentin Review (Valentin, 2026-10-03: "the agent must check that the task it suggests isn't already claimed/done"). Suggest only; claim it when he says go.
- **Agents are human companions** (Valentin, 2026-10-02: "if I add myself to the ticket as the human assignee, the agent mustn't remove me"). A ticket usually has a human assignee and an agent together; agent-only is fine. Never remove or change a human assignee, never add Valentin yourself, and never use a command that replaces the assignee list.
- **Improve the Agent Kit when it blocks you** (Valentin, 2026-10-02: "i want to enable runners to contribute to the agent setup"). When a skill, script or check gets in your way, fix it yourself instead of working around it:
  1. Search board 4060 (Agents & Infra) for a ticket about it first; only if none exists, create one there via `vcc`. If another session already has it in flight, comment there instead of fixing it twice.
  2. Same path as app code: branch, PR named after that ticket, tests (`.claude/skills/ship/scripts/*.test.sh` for /ship scripts), AI review, merge when green.
  3. Fix only what blocked you, then go back to your own ticket. No redesigns on the side.
  4. **Protected parts:** do not merge changes to these yourself: `ship-gates`, the `guard` part of `ship-check` (the merge and Done blocks), `ship-identity`, the `vcc` wrapper, `.claude/skills/unlazy/`, `.claude/hooks/`, `.claude/settings.json`, `CLAUDE.md` and `AGENTS.md`. Open the PR, then send its link to the INFRA MANAGER session (Claude: `SendMessage` to `INFRA MANAGER`; Codex: a comment on the ticket naming Infra Manager). Infra Manager reviews and merges.
- **Old automated comments do not count (Valentin, 2026-10-01).** The automated agents were retired on 2026-10-01. Their claims, "Blocked" notes, decisions, plans and progress on a ticket are history, not state. Authors include Product Bot, Dev 1, Dev 2, Feature Dev 1, QA 1, Supervisor and any "worker" or "drain" bot. A ticket with only such comments is free: pick it, claim it via `vcc` and treat the ticket as open. Read those comments only for facts about the ticket (steps, screenshots, error text), and re-check those facts on the live site. Whether a ticket is taken follows the rule above, read from the ticket alone.

Nothing is "live" until the Production deployment for the merge sha is `success` and you verified the change on app.hypertask.ai with evidence on the ticket.
